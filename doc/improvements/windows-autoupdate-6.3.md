# Windows automatic updates in OpenRocket MIT 6.3

The MIT edition checks only `MDNich/ActiveControl_MIT_RktTeam` on GitHub. Upstream OpenRocket release checks are disabled. Startup checks respect the existing update preference; **Help → Check for updates** and **Preferences → Check now** check the MIT feed even when startup checks are disabled, and include versions previously skipped at startup. The irrelevant upstream beta-update option is hidden in MIT builds.

## User workflow

1. The update dialog shows the newer MIT version and its release notes.
2. **Download and Install** first offers to save or discard unsaved designs. Cancel leaves the application open and does not start installation.
3. The application downloads the release JAR and verifies its SHA-256 checksum. The Windows helper copies it alongside the installed JAR and verifies that copy again before declaring itself ready.
4. OpenRocket quits only after staging succeeds. The helper waits for the process to exit, replaces the JAR, and retains the previous JAR as `<installed-jar>.bak`. Temporary file locks are retried for up to 60 seconds.
5. The app restarts using `OpenRocket MIT.exe` (with older launcher names supported). A standalone JAR restarts with the same Java installation it was already using, including paths with spaces or non-ASCII characters.

Writable, per-user installations do not request administrator access. Protected installations request Windows elevation for the replacement worker; the separate restart process retains the original user's privileges. Preparation failures leave OpenRocket running. Failures after shutdown are logged and displayed by the helper. A cancelled or timed-out preparation marks the update cancelled so a delayed helper cannot install it later.

The log is written to `%USERPROFILE%\Downloads\openrocket-mit-update.log`, or the home directory if Downloads cannot be created. The downloaded update directory also retains helper status/output for troubleshooting.

These are **JAR updates**. They preserve the launcher, bundled Java runtime, shortcuts and installer registration. Updating those components requires a full installer. The version in Windows' installed-apps listing can therefore remain at the original installer version; OpenRocket's About dialog reports the updated MIT version.

## Assets to publish

For release 6.3, publish these two files together on the GitHub release with tag `v6.3`:

- `OpenRocket-MIT-v6.3.jar`
- `OpenRocket-MIT-v6.3.jar.sha256`

Both are now generated by `shadowJar` under `clone/openrocket/build/libs/`. The checksum contains the SHA-256 hash and exact JAR filename. The existing retriever can also use the digest supplied by GitHub's release-asset metadata. A Windows EXE or macOS `.app.zip` alone is insufficient for this updater. Publish a normal, non-draft, non-prerelease release that GitHub selects as the latest release, with a version newer than the installed MIT version.

Publishing these assets makes the update available to older installations. Existing 6.1/6.2 installations retain their previous helper until upgraded; their first upgrade may still request elevation. If that older helper fails, install this build manually once. Subsequent upgrades use the new helper.

## Verification

The repeatable checks are in `packaging/verification/WindowsUpdateProbe.java`, `UpdateRestartAgent.java`, `verify-windows-update.ps1` and `verify-windows-update-worker.ps1`. They use disposable copied app images and a loopback download server. They do not update an installed application or publish a release. External HTTPS is blocked in the test JVMs.

Unit coverage checks MIT-only startup routing, launcher discovery, the current-Java fallback and literal PowerShell argument encoding. Windows helper checks cover incorrect checksums, cancellation while waiting, file-lock retry, original-JAR preservation and backup content. End-to-end checks cover both native launcher and standalone-JAR restarts, including observation of the restarted main window.

On September 26, 2026, all five focused Java tests and all six Windows scenarios passed: checksum rejection, native-launcher restart, standalone-JAR restart, locked-file retry, cancellation and staged-checksum rejection. Both restart checks observed the main application window. The restart checks ran as the logged-in Windows user with no elevation; earlier service-session graphics failures were isolated to the verification setup.

Evidence is under `clone/openrocket/build/windows-update-verification/` (`windows-results.json`, `worker-results.json`, and per-case logs). The available host is Windows 11 ARM64 in Parallels using the packaged x64 Java runtime under emulation. Interactive UAC prompts and native Intel/AMD Windows hardware require separate verification.

The helper follows Microsoft's documented [Start-Process argument quoting and process behavior](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process?view=powershell-5.1) and uses [File.Replace with a backup](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=netframework-4.8.1) for the installed JAR.
